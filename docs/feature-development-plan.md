# 功能开发计划

更新日期：2026-08-04

当前状态：R1-R7 已实现，等待用户检查与验收。后续新需求继续追加到同一架构与实施顺序中。

## 0. 协作与开发流程

当前采用“先完整收集，再统一排期”的方式：

1. 用户逐项描述需求期间，只更新本文档，不修改应用代码，不执行检查、测试或构建；该阶段现已结束。
2. 每项需求分别记录目标、用户流程、范围、待确认点和验收标准；存在冲突时先记录，不立即以代码方案解决。
3. 在用户明确表示“需求说完了”之前，不开始新一轮开发。
4. 需求收集结束后，统一复查完整计划，识别需求之间的依赖、冲突和可合并实现项。
5. 开发顺序优先合并会修改同一状态模型、组件或交互链路的需求，减少对相同代码的反复更新。
6. 统一开发顺序已确认，当前开始修改代码。
7. 后续检查、测试和构建由用户执行，除非用户重新明确要求助手执行。

### R2 坐标轴与元素组合边界

#### 已确认需求

1. 直角坐标轴和极坐标轴都是依附于元素的组件，不是独立、无归属的画布元素。
2. 元素可以参与 `Group` 和 `Ungroup`。
3. 坐标轴不属于 `Group` 和 `Ungroup` 所处理的结构范围。
4. 直角坐标轴与极坐标轴使用相同的归属和组合边界规则。
5. 只有元素可以被直接拖拽；坐标系本身不能作为独立画布元素拖拽。
6. 元素移动时，与它关联的坐标系随元素一起移动。
7. 系统必须显式记录元素与坐标系之间的关联，不能只依赖当前 SVG 层级或视觉位置推断。
8. 一个坐标系可以被多个元素共享，并且需要记录具体共享哪些坐标维度。

#### 当前语义

- “依附于元素”表示坐标轴需要保留明确的所属元素关系。
- “在 Group/Ungroup 范围之外”表示执行组合或解组时，不把坐标轴作为普通 child 加入、移出或拆散。
- 坐标轴的生命周期和显示仍由所属元素决定，而不是由 Group 的 children 数组决定。
- 元素是可选中和拖拽的主体；坐标系是由关联关系驱动的附属编辑组件。

#### 关联模型要求

至少需要表达下面三类关系：

1. 元素属于哪个坐标系。
2. 元素使用该坐标系的哪些维度或通道。
3. 一个坐标维度的编辑需要传播到哪些共享元素。

建议在统一设计阶段形成类似下面的语义关系，但当前不提前固定最终类型定义：

```text
CoordinateSystem
  members:
    - elementId
      sharedChannels: [x, y]
    - elementId
      sharedChannels: [x]
```

直角坐标系至少需要区分 `x`、`y`；极坐标系需要区分径向维度和 ring/环向维度。最终通道命名在需求收集结束后统一确定。

#### Layer 共享规则

1. `Layer` 中 Line Chart 的 lines 和 Scatterplot 的 points 可以属于同一个共享坐标系。
2. 当这些元素共享完整直角坐标系时，点击任一相关元素只显示一套共享坐标轴，不能为每个元素重复显示坐标轴。
3. 对共享坐标轴执行 X/Y 编辑时，修改同时传播到该坐标系内所有使用对应通道的元素。
4. 拖拽共享坐标轴的 scale 控件时，所有共享该通道的元素同步更新位置或尺度映射。
5. 坐标轴编辑的传播范围由坐标系成员关系决定，不由当前点中了 line 还是 point 决定。

#### Concat 部分共享规则

1. `Concat` 不一定共享完整坐标系，可以只共享一个维度。
2. 直角坐标系可能只共享 `x` 或只共享 `y`。
3. 极坐标系可能只共享径向维度或 ring/环向维度。
4. 调整某一共享坐标轴或 scale 时，只影响声明使用该维度的元素。
5. 未共享的其他维度保持各自独立，不应因一次坐标编辑被连带修改。

#### 编辑传播示例

| 组合 | 共享维度 | 编辑操作 | 影响范围 |
| --- | --- | --- | --- |
| Layer: lines + points | `x`、`y` | 修改 X 或拖拽 X scale | 所有共享 X 的 lines 和 points |
| Layer: lines + points | `x`、`y` | 修改 Y 或拖拽 Y scale | 所有共享 Y 的 lines 和 points |
| Concat | 仅 `x` | 修改 X 或拖拽 X scale | 仅所有共享 X 的元素 |
| Concat | 仅 `y` | 修改 Y 或拖拽 Y scale | 仅所有共享 Y 的元素 |
| Polar Concat | 仅径向 | 修改径向 scale | 仅所有共享径向维度的元素 |
| Polar Concat | 仅 ring/环向 | 修改 ring/环向设置 | 仅所有共享该维度的元素 |

#### 待确认行为

- 所属元素缩放或旋转时，坐标轴分别需要如何跟随；移动已确认为随元素一起移动。
- Group 整体移动、缩放或旋转时，成员元素的坐标轴是否跟随最终视觉变换。
- 点选坐标轴时，是选中轴组件、所属元素，还是进入轴编辑状态。
- 元素被删除、复制或粘贴时，附属坐标轴的生命周期和复制规则。
- bbox、框选和对齐计算是否排除坐标轴的视觉范围。
- 坐标轴的层级顺序是否始终位于元素内容之上，以及是否受 Bring to front / Send to back 影响。
- 极坐标的“ring/环向”最终对应 angle、ring index、环带范围还是其他通道命名。
- Concat 中共享维度由系统自动推断、组合模板预设，还是由用户选择。

#### 初步验收方向

1. 对元素执行 Group/Ungroup 后，坐标轴不会变成普通 Group child，也不会因解组被拆成独立元素。
2. 坐标轴始终能够追溯到唯一的所属元素。
3. 直角坐标轴和极坐标轴在组合边界上行为一致。
4. 拖拽元素时，关联坐标系随之移动，但坐标系不能被当作独立元素拖拽。
5. Layer 中共享完整坐标系的多个元素只显示一套坐标轴。
6. 编辑共享 X/Y 或拖拽对应 scale 时，所有共享该维度的元素同步更新。
7. Concat 只共享单一维度时，坐标编辑不会影响未共享的其他维度。

### R3 模板内部元素的语义分组与配置同步

#### 术语边界

本需求中的“group 信息”指图表模板内部 marks 的语义分组，例如同一个 Line Chart 中属于同一角色的多条 line，或同一个 Scatterplot 中属于同一角色的多个 point。它不同于画布结构中的 `Group/Ungroup`：

| 概念 | 作用 |
| --- | --- |
| Canvas Group | 组织画布节点，支持整体移动、进入内部编辑和 Ungroup |
| Template/Mark Group | 记录同一图表内部元素的语义同类关系，并传播配置 |

#### 已确认需求

1. Line Chart、Scatterplot 以及未来新增模板中的内部元素需要自动记录稳定的语义 group 信息。
2. 同一语义 group 内的元素需要知道彼此属于同一模板角色或同一生成规则。
3. 编辑其中一个元素时，同组其他元素自动配置为相同。
4. 该同步机制不能只针对当前 Line Chart 或 Scatterplot 写死，需要能够扩展到未来模板。
5. 自动生成的新 marks 也需要继承对应的语义 group 和共享配置。

#### 需要保存的信息

统一设计时至少需要覆盖：

- 所属 chart/template 实例。
- 模板中的 mark role，例如 `line`、`point` 或未来的其他角色。
- 语义 group ID。
- 数据 series/group key；它用于区分数据分组，但不一定等同于配置同步 group。
- 该组共享的配置引用或配置版本。
- 单个元素是否允许覆盖组配置。

#### 配置传播方向

```text
编辑一个 mark
  -> 找到该 mark 的 Template/Mark Group
  -> 更新 group-level 配置
  -> 同组其他 marks 读取相同配置
  -> 重新渲染受影响的 marks
```

#### 待确认行为

- “配置为相同”具体包含哪些属性：颜色、线宽、点大小、形状、透明度、数据 encoding、坐标通道或其他属性。
- 单个 mark 是否允许显式退出同步，形成局部 override。
- 不同数据 series 是否共享样式配置，还是只共享结构与 encoding 规则。
- 同一模板中不同 mark role 之间是否可以建立联动配置。
- 复制、Facet、Layer 或 Concat 后，语义 group ID 是继承、派生还是重新创建。

#### 初步验收方向

1. 同一模板实例中的 marks 具有稳定、可查询的语义 group 信息。
2. 编辑任一组成员后，其他组成员自动获得相同的组级配置。
3. 数据变化导致 marks 数量变化时，新 marks 自动加入正确的语义 group。
4. 新模板可以声明自己的 mark roles 和同步规则，而不需要重写通用选择与传播机制。

### R4 数据维度推断与嵌套方案推荐

#### 已确认需求

1. 数据绑定完成后，系统需要自动分析数据维度和重复结构，而不是只绘制单一序列。
2. 以当前 Line Chart 为例：X 绑定时间、Y 绑定体重后，如果数据表现为 `1 * n` 记录并存在 5 个分组，则应在同一个 Line Graph 中直接绘制 5 条 line。
3. Scatterplot 和未来模板也需要根据其 mark 语义推断应生成的 marks 和分组数量。
4. 如果基础 series 分组之外还存在更外层维度，系统需要给出可执行的嵌套方案推荐。
5. 推荐方案至少包含：展平该外层维度，或生成多个图表并通过 Facet 表达。
6. 数据维度可以驱动多层嵌套方案，不应把所有额外维度都强制塞入一个图表。

#### Line Chart 基础推断示例

```text
已绑定：
  x = time
  y = weight

检测到：
  series 候选产生 5 个稳定分组
  每组包含 n 个按 time 排序的记录

默认结果：
  一个 Line Graph
  五条 line
  每条 line 对应一个 series key
```

这里的 5 条 line 应加入 R3 定义的 line mark group，共享模板级配置，同时各自保留数据 series key。

#### 外层维度与推荐方案

当绑定 X/Y 和基础 series 后仍存在具有分组意义的外层维度时，系统不直接做唯一假设，而是生成推荐表：

| 方案 | 处理方式 | 适用方向 |
| --- | --- | --- |
| 展平 | 将外层维度合并到现有 series、样式或其他 encoding 中 | 维度基数较低且单图仍可读 |
| Facet | 每个外层维度值生成一个 Line Chart/其他图表 | 需要比较多个独立视图 |
| 嵌套组合 | 将外层维度映射为更高层组合，内部保留基础图表 | 数据本身具有层级结构 |

推荐项需要明确展示：使用了哪个维度、预计生成多少 marks 或图表、共享哪些坐标通道，以及是否会产生更深层嵌套。

#### 推断层级

1. 推断字段类型和已绑定通道。
2. 推断基础 mark 分组，例如 Line Chart 的 series。
3. 计算每个候选分组的记录覆盖率、X 唯一性、组数和组大小。
4. 直接生成置信度足够高的基础 marks。
5. 检查剩余维度是否形成稳定的外层分组。
6. 对外层分组生成展平、Facet 或嵌套方案推荐。
7. 用户确认推荐后，再建立相应组合结构和坐标共享关系。

#### 与其他需求的关系

- R3 负责记录自动生成 marks 的语义 group，并同步同类配置。
- R2 负责记录同一图表或多个 Facet/Concat 视图共享哪些坐标维度。
- R1 负责让用户进入生成后的结构中继续点选和编辑内部元素。

#### 待确认行为

- 基础 series 推断达到什么置信度时可以自动执行，什么情况下必须询问用户。
- 推荐表在界面中的位置、排序方式和确认交互。
- “展平”可以使用哪些通道，以及如何避免颜色、形状或线型数量过多。
- 外层维度超过一层时，推荐深度是否有限制。
- Facet 生成后是共享完整坐标系、共享单一维度，还是每个视图独立；这需要结合 R2 的规则决定。
- 数据更新后，已确认的推断和嵌套方案如何增量更新。

#### 初步验收方向

1. X=time、Y=weight 且存在 5 个稳定 series 时，一个 Line Graph 自动生成 5 条 line。
2. 每条 line 保留稳定 series key，并加入正确的 Template/Mark Group。
3. 存在外层维度时，系统提供至少“展平”和“Facet”方案，而不是静默丢弃该维度。
4. 推荐项说明预期结构、数量和坐标共享方式。
5. 用户选择方案后，生成结果与 R1-R3 的选择、配置同步和坐标传播规则兼容。

### R5 基础 Chart Template 维度映射表

#### 已确认需求

1. 每一个基础 Chart Template 都必须具有一份维度映射表。
2. 映射表描述该模板支持的数据维度、视觉通道和 mark roles 之间的对应关系。
3. 数据绑定、自动分组推断、marks 生成和外层嵌套推荐都读取该映射表，不能为每种图表单独写死规则。
4. Line Chart、Scatterplot 以及未来新增的基础模板遵循同一份映射表契约。

#### 映射表至少需要表达

- 模板支持的必需和可选数据维度。
- 数据维度可绑定的视觉通道。
- 每个通道允许的数据类型。
- 哪个维度用于生成 mark、series 或更外层分组。
- 维度对应的 Template/Mark Group。
- 可共享的坐标维度，以及未使用维度的推荐处理方式。

最终字段结构和命名在需求收集结束后统一设计。

#### 初步验收方向

1. 任一基础模板都能查询到自己的维度映射表。
2. 推断引擎可以仅根据数据 schema、已绑定字段和映射表生成候选绑定及分组方案。
3. 新增模板时，通过补充映射表接入通用推断流程，不需要复制一套图表专用判断代码。

### R6 扩展基础图表与组合按钮

#### 当前基线

- 已有一个 Line Chart 实现，可作为统一模板契约、数据绑定和组合行为的第一份参考。

#### 已确认需求

1. 在 Line Chart 之后实现 Scatterplot、Pie Chart、Matrix 和 Donut 基础模板。
2. 每个新增模板都需要满足 R3 的 mark group、R4 的数据维度推断和 R5 的维度映射表要求。
3. Scatterplot 需要支持 point marks 的自动生成、语义分组和共享坐标通道。
4. Pie Chart 和 Donut 需要按极坐标语义声明维度映射、mark group 和可共享通道。
5. Matrix 需要声明自己的行、列、cell/mark 等维度关系，具体映射在统一设计阶段确定。
6. 实现并统一 Layer、Concat、Facet 按钮的组合流程。
7. 按钮组合与 R7 的拖拽组合必须调用同一套底层组合命令，不能形成两套不同的数据结构或传播规则。

#### 组合按钮要求

| 按钮 | 基础结果 | 坐标关系 |
| --- | --- | --- |
| Layer | 多个元素叠加到同一组合视图 | 可以共享完整或声明的坐标通道 |
| Concat | 多个视图沿指定方向连接 | 可以只共享一个直角或极坐标维度 |
| Facet | 根据数据外层维度生成重复视图 | 共享范围由维度映射和方案确认决定 |

#### 待确认行为

- Matrix 的准确图表语义、marks 类型和默认维度映射。
- Pie Chart 与 Donut 的角度、半径、ring/环向通道如何命名。
- 各模板第一阶段需要支持的样式编辑范围。
- Layer、Concat、Facet 按钮是否先打开方案预览，还是在唯一方案时直接执行。
- 不兼容模板参与组合时的提示和可选转换方案。

#### 初步验收方向

1. 五种基础模板都具有维度映射表和稳定 mark group。
2. 每种模板可根据绑定数据生成正确数量和角色的 marks。
3. Layer、Concat、Facet 按钮生成语义组合结构，并正确声明共享通道。
4. 按钮创建的组合与拖拽创建的同类组合具有相同的数据模型和后续编辑行为。

### R7 拖拽 Card 到组合热区自动 Layer/Concat

#### 已确认需求

1. 用户可以把 Chart Card 直接拖入一个已经设定好坐标轴的 Chart。
2. 已配置 Chart 的内部需要存在一个 Layer 投放区域。
3. Card 拖入该内部区域并释放时，自动与目标 Chart 进行 Layer 合成。
4. 已配置 Chart 的坐标轴边界需要存在 Concat 投放区域。
5. Card 拖到某个坐标轴边界区域并释放时，自动执行 Concat，并把该边界对应的轴声明为共享维度。
6. 拖拽组合与按钮组合使用相同的兼容性判断、维度继承、组合数据结构和 Undo/Redo 行为。

#### Layer 热区

```text
Chart 内部绘图区
  + Card drag enter
  + 命中 Layer 热区
  + 显示 Layer 目标反馈
  + drop
  -> 创建 Layer
  -> 新元素继承或确认目标坐标系的共享通道
```

Layer 热区应与普通画布投放明确区分，只有进入目标 Chart 的有效内部区域时才触发自动组合。

#### Concat 边界热区

```text
Chart 坐标轴边界
  + Card drag enter
  + 命中某一轴的 Concat 热区
  + 高亮将共享的坐标维度
  + drop
  -> 创建 Concat
  -> 仅共享该热区代表的轴或坐标通道
```

直角坐标边界至少需要区分共享 `x` 和共享 `y`。极坐标边界后续需要对应径向和 ring/环向共享规则。

#### 拖拽状态与反馈

- 未进入热区：保持普通 Card 拖入画布行为。
- 进入 Layer 热区：显示目标内部区域和 Layer 状态。
- 进入 Concat 热区：高亮具体边界，并显示将共享的坐标维度。
- 目标不兼容：不执行隐式组合，并显示不可投放状态。
- 离开热区或取消拖拽：清除所有临时反馈，不修改画布结构。

#### 与数据推断的关系

1. 目标 Chart 已配置坐标通道时，新 Card 可以继承兼容的绑定。
2. 缺少的维度通过 R4 推断，并结合 Card 对应的 R5 维度映射表生成建议。
3. 存在多个有效映射时，不静默选择，需要进入方案确认流程。
4. Layer 完成后按 R2 记录共享坐标系成员和通道。
5. Concat 完成后只记录热区所代表的共享维度，其他维度保持独立。

#### 待确认行为

- Layer 内部热区覆盖整个 plot area，还是仅覆盖中心区域以避免与 Concat 边界冲突。
- Concat 在 X/Y 轴两端或上下左右边界的具体布局方向。
- Card 是模板 Card、已有画布元素，还是两者都支持拖入热区。
- Drop 前是否显示组合后的实时预览。
- 目标已有 Layer/Concat 时，继续拖入是追加到现有组合还是创建嵌套组合。
- 极坐标 Layer/Concat 热区的几何形状和优先级。

#### 初步验收方向

1. Card 拖入已配置 Chart 的内部 Layer 热区后生成 Layer，而不是普通重叠元素。
2. Card 拖到 X 或 Y 边界热区后生成 Concat，并只共享相应轴。
3. 热区在拖拽过程中具有明确、互斥的视觉反馈。
4. 不兼容或未命中热区的 Drop 不会意外创建组合。
5. 拖拽和按钮创建的组合可以用同一套后续选择、坐标编辑和数据推断流程处理。

### R8 Pie Chart 拖入 Scatterplot 生成 Nested Pie

#### 已确认需求

1. Pie Chart 模板必须拖到已绑定 X/Y 的 Scatterplot 具体散点上，才进入专用 Nested 投放区；拖到绘图区空白处不触发。
2. 每次 Drop 只在命中散点对应的数据行位置生成一个小 Pie Chart；继续拖到其他点时追加，不清除已生成点位。
3. Case 1 优先使用 `water_kg`、`fat_kg`、`muscle_kg`、`minerals_kg` 四个分量字段。
4. 首选字段不存在时，从未占用的 quantitative 字段中取前四个；不足四个时投放区显示不可用。
5. Nested Pie 使用 Scatterplot 的同一组 X/Y scale，坐标绑定、轴反转和 scale 调整后随散点重新定位。
6. 拖放结果写入目标 Scatterplot 的 `nestedSpec`，不创建额外 Canvas Group。

#### 初步验收方向

1. Pie Chart 进入具体散点的命中半径时显示独立于 Layer/Concat 的小型 Nested 热区反馈。
2. Drop 后只有被命中的散点对应一个包含四个 arc 的 Pie。
3. Pie 各 arc 的比例与对应数据行的四分量一致。
4. 重新绑定或缩放 Scatterplot 坐标轴后，Nested Pie 不脱离对应散点。

## 统一实施顺序

为避免多次修改相同的状态与渲染入口，R2-R7 合并为四个阶段：

1. **公共语义模型**：定义五类模板的维度映射表、稳定的 Template/Mark Group、坐标系 owner/member/sharedChannels，以及 Layer/Concat/Facet 的统一组合结构。
2. **推断与基础渲染**：数据绑定统一读取模板契约；实现 Line、Scatterplot、Pie、Donut、Matrix 的确定性渲染、series 自动推断和外层维度方案推荐。
3. **统一组合命令**：按钮和拖拽共同调用同一个命令；Line + Scatter Layer 保持同层 Line Group/Point Group，Facet/Concat 保持同层独立 View，必要的 Nested 结构才使用 Canvas Group。
4. **拖拽热区与反馈**：在已配置图表内部提供 Layer 热区，在坐标边界提供 Concat 热区；处理互斥高亮、不兼容反馈和普通投放回退。

### 实施决策

- 坐标系仍由一个 Canvas 节点负责显示和定位，但通过 `coordinateSystem` 显式保存 owner、成员和共享通道；坐标轴不会进入 `children`。
- Canvas Group、Template/Mark Group、数据 series 使用不同 ID 和字段，彼此不混用。
- 基础模板用 declarative dimension mapping 接入通用推断器；不在数据绑定 UI 中按图表类型堆叠分支。
- Line + Scatter Layer 不使用外层 Canvas Group；Line Group 输出坐标轴和折线，Point Group 只输出散点 marks，两者以共享 `compositionSpec.id` 和 `coordinateSystem.id` 保持合成关系。
- 第一阶段对未明确的 Matrix 采用 `row + column + value -> cell`；Polar 采用 `angle + radius/ring` 命名。
- 所有实现完成后由用户执行检查、测试、构建与浏览器验收。

### 本轮实现记录

- 新增 `chartTemplates.ts`，集中声明 Line、Scatter、Pie、Donut、Matrix 的维度映射、mark role、坐标类型、共享通道和剩余维度策略。
- 新增 `dimensionInference.ts`，自动推断 Line/Scatter series，生成稳定 Mark Group，并为外层维度生成 Flatten、Facet、Nested 可执行建议。
- Canvas 节点新增显式 `coordinateSystem`、`compositionSpec`、`markGroups` 和维度建议；Canvas Group、Mark Group、series key 使用独立字段。
- Line、Scatter、Pie、Donut、Matrix 统一进入确定性渲染入口；生成 marks 带稳定 `data-mark-group-id` 和数据身份。
- mark inspector 增加组级颜色、透明度、线宽或点大小编辑；修改一个 mark 后由共享配置重新渲染同组 marks。
- 坐标绑定、方向和 scale 修改按 `sharedChannels` 传播；直角坐标支持 `x/y`，极坐标支持 `radius/ring` scale。
- Layer 按钮创建带真实 children 的组合节点；Concat/Facet 按钮创建可单独点选的同层 View，但共享组合 spec 和声明的坐标通道。
- Facet 按数据外层维度创建过滤后的重复视图；Concat 按共享通道记录部分共享关系。
- Card 拖拽增加内部 Layer 热区和边界 Concat 热区，包含兼容、不可投放和取消清理状态；拖拽与按钮共用组合命令。
- Group/Ungroup 不把坐标轴变成 child；解组组合时重新归属共享坐标 owner，并保留成员关系。
- 左侧模板列表置顶展示 Line、Scatter、Pie、Donut、Matrix 五个内置 SVG 可视化拖拽卡片；这些候选不依赖外部图库是否存在对应文件，并保留完整图库作为补充。
- 直角坐标配置入口位于轴线中点的设置按钮，端点仅保留方形 scale 手柄，不再使用圆形配置按钮。
- 外层维度建议通过独立 popup 展示，Flatten、Facet、Nested 作为包含维度、数量、marks 和共享通道信息的可点击方案卡。

## 1. 功能概述

- 功能名称：组合内部编辑模式
- 目标用户：在画布中编辑手动 Group 或自动组合结果的作者
- 要解决的问题：当前 Group 只能作为顶层整体选中，若不 Ungroup 就无法选择和操作内部元素
- 预期结果：用户可以像 PowerPoint 一样双击进入 Group，在保持组合结构的前提下编辑内部元素

## 2. 已确认需求

1. 双击具有结构化子节点的 Group 后进入该 Group 的内部编辑模式。
2. 进入后可以单击和拖动 Group 的直接子元素，不需要先 Ungroup。
3. 内部元素沿用现有的多选、删除、复制粘贴、Group、Ungroup、层级调整和对齐能力。
4. 遇到嵌套 Group 时，可以继续双击逐层进入。
5. 按 `Esc` 逐层退出；点击当前 Group 之外的画布或其他顶层对象时退出内部编辑模式。
6. 手动 Group 和自动组合产生的结构化 Group 使用相同交互。
7. 没有结构化子节点、仅保存渲染结果的语义图表不进入空的内部编辑模式，以免破坏数据语义。
8. 内部编辑与外部编辑使用同一套交互：点选、修饰键多选、空白区域框选、bbox、缩放和旋转均应可用。
9. 工具栏与右键菜单按钮对当前编辑层级生效，进入 Group 后不应仅因层级变化而禁用。

## 3. 用户流程

1. 用户单击 Group：选中整个 Group，拖动时移动整体。
2. 用户双击 Group：进入内部编辑模式，Group 本身保持不拆分。
3. 用户单击内部元素：选中该元素；拖动时只移动该元素。
4. 用户使用修饰键单击：在当前 Group 层级内多选或取消选择元素。
5. 用户双击内部 Group：进入下一层 Group。
6. 用户按 `Esc`：回到上一层并选中刚退出的 Group。
7. 用户点击组外：退出内部编辑模式并按正常画布规则处理本次点击。
8. 用户在组内空白区域拖动：框选当前 Group 的直接子元素，不退出内部编辑。
9. 选中内部元素后：显示与顶层一致的 bbox、缩放手柄和旋转手柄。

## 4. 范围

### 本次包含

- 基于 Group 层级的编辑作用域。
- 内部元素的选中反馈和拖动。
- 嵌套 Group 的逐层进入与退出。
- 现有编辑命令对当前作用域的适配。
- 组内框选、bbox、缩放和旋转。
- Undo/Redo 对内部编辑作用域和选择状态的恢复。

### 本次不包含

- 将只有 `renderedContent`、没有子节点的语义渲染结果自动拆成 SVG path。
- 跨 Group 层级同时多选。
- 一次双击后直接选择任意深度的后代元素。

## 5. 交互与界面

- 当前正在编辑的 Group 显示独立虚线边界。
- 当前层级内被选中的元素显示与顶层一致的 bbox、缩放手柄、旋转手柄和选中高亮。
- 框选框和 bbox 在当前 Group 的局部坐标中计算，再随 Group 的完整变换渲染到画布。
- 不新增常驻说明文字，进入和退出由双击、`Esc` 及边界反馈完成。

## 6. 数据与状态

- `editingGroupPath` 保存从顶层 Group 到当前编辑 Group 的 ID 路径。
- `selectedIds` 始终表示当前编辑作用域的直接子节点；未进入 Group 时表示画布顶层节点。
- Group 结构本身不因进入或退出编辑模式而改变。
- 编辑路径属于临时 UI 状态，不写入项目持久化；Undo/Redo 快照会保存它，以恢复连续编辑体验。

## 7. 技术方案

- 在 `useCanvasStore` 中增加当前 Group 路径和“当前选择作用域”解析。
- 让选择、移动及编辑命令读取当前作用域，而不是固定读取 `canvasNodes` 顶层数组。
- `CanvasNodeView` 根据编辑路径，只让当前 Group 的直接子节点接收指针事件。
- 组内拖动使用当前 Group 的 SVG 局部坐标，兼容画布缩放及 Group 自身变换。
- 框选、缩放和旋转交互同样使用当前 Group 的 SVG 局部坐标。
- 选择覆盖层使用当前 Group 的累计变换矩阵，保证 bbox 与内部元素重合。
- 纯 `renderedContent` 节点继续使用现有语义 mark 事件，不做隐式 SVG 拆解。

## 9. 验收标准

1. Group 未进入编辑模式时，单击和拖动仍操作整个 Group。
2. 双击 Group 后，单击并拖动一个直接子元素只改变该子元素的位置，Group 不被拆开。

7. 现有顶层选择、拖动、组合和语义 mark 点击行为不回归。
8. 在 Group 内拖动空白区域只框选当前层级的直接子元素，并显示框选矩形。
9. 内部单选或多选后显示 bbox，缩放和旋转操作只修改当前层级的选中元素。
10. 工具栏与右键菜单的可用状态及执行范围与顶层一致，但只作用于当前 Group 层级。
